# DENTIX cutover and recovery runbook

Status: PREPARED, NOT EXECUTED. This PR grants local preparation and a Draft PR only. Every production, DNS, hosting, account, indexing and synthetic-delivery step below requires a separate exact authorization. No launch date or named operator is assumed. The production release archive is not a complete deployable migration adapter.

Use `checklists.json` as the execution record: assign each owner, attach sanitized evidence, timestamp and mark the result. A missing required item is a NO-GO. Keep backups, access logs and private exports in owner-controlled storage; reference receipts and hashes here, never patient records or credentials.

## Pre-cutover — release owner and hosting owner

1. Confirm exact repository commit, release archive SHA-256, route manifest and extracted `SHA256SUMS.txt`. Run `python3 scripts/release.py verify` on the reviewed artifact. Freeze medical/source changes. Record qualified dental review sign-offs from `ops/review/professional-review.json`; pending decisions block production.
2. Hosting owner exports WordPress database, `wp-content` (including uploads/plugins/themes), rewrite/vhost/CDN/headers configuration and full DNS zone. Encrypt backups in owner storage, capture sizes/hashes/UTC time, restoration instructions and retention owner. Rehearse restoration to an isolated origin, compare critical public URLs/media and record recovery duration. Target recovery <=15 minutes; an unproven target blocks launch.
3. Record TLS chain/SAN/expiry, verification files/tags, robots and all sitemap endpoints, critical URL content fingerprints, original TTLs and mail-related records. Identify independent legacy origin address and Host/SNI configuration. Do not proxy the new public domain back to itself.
4. Resolve all 49 HOLD rows or approve and test a preservation method for each. Preferred conditional design: exact GET/HEAD legacy-origin proxy, preserving path/query/status/content type and dependent media. Scope allowlist to known legacy URLs/dependencies; do not expose admin/login or create an open proxy. Test redirects for loops. Do not cache personalized responses. Static preservation requires a complete dependency inventory and approved provenance. Neither option is implemented by PR05.
5. Obtain owner decisions for the proposed 410 maintenance page and all planned 301s. Test all 64 sources and their query variants on noindex staging against `migration-contract.json`; include real 404 `/sitemap_index.xml`. WordPress sitemap redirects stay inactive until the replacement sitemap is 200 and validated. Inventory log-only aliases and functional `?p=`, `?page_id=`, `?attachment_id=`, `?feed=` and search queries; preserve them or obtain explicit decisions. Never let functional queries resolve to an unrelated homepage.
6. Select host only after `hosting-decision.json` minimum evidence passes. Build a reviewed host adapter and staging test receipt. Twelve static patient routes, assets and a real custom 404 must precede generic fallback rules. Test exact server 301/410, HTTPS/www, headers, caches, logs, version marker and rollback. The local artifact server is not a production redirect adapter.
7. If an authorized DNS switch needs lower TTLs, propose 300 seconds at least one current TTL period before switch. Owner approves exact records and verifies propagation; preserve NS/MX/TXT/CAA unless separately authorized. Record previous values and rollback commands in owner-controlled run sheet.
8. Confirm the environment contract. This candidate uses fallback content, empty content/lead/booking endpoints and booking=false. Choosing an enabled backend requires separate endpoint, consent, origin/CORS, privacy, review and delivery authorization. Do not inherit the preview workflow's booking=true.
9. Capture T0 for 28/90 settled days using `access-t0.json`; preserve old analytics/verification configuration and define approved consent behavior. Missing data remain unknown. A release owner may only accept measurement gaps through a separate documented launch decision; PR05 cannot waive them.
10. Name launch operator, clinical reviewer, monitoring owner and rollback owner; approve window, maintenance/change freeze and recovery target. Record explicit go/no-go and exact mutation authorization. No production step begins while these slots or required evidence are empty.

## Cutover — only after a separately authorized GO

1. Freeze changes; verify archive checksum and source SHA again. Extract only `artifact/` as static site content; manifests stay as operator records except an explicitly reviewed version marker.
2. Upload to versioned release storage; do not overwrite the old origin/backup. Attach domain or atomically select release according to reviewed host adapter. Apply HTTPS/apex normalization preserving raw path/query, exact 301/410 and the tested HOLD preservation layer. Preserve unrelated DNS/mail services.
3. Serve custom 404 with HTTP 404 and no canonical. Never use an SPA homepage fallback. Ensure no mixed releases across CDN/origin. Purge only authorized site caches. Confirm deployed source SHA through a reviewed header/version endpoint.
4. Run GET and HEAD for all 12 routes at apex plus HTTP/www variants, all 64 migration rows and missing/admin probes. Require 12/12 patient 200, unique metadata, self-canonical, `index,follow`, clean asset URLs, 12 sitemap URLs, robots sitemap pointer and no bot-specific block. Googlebot/Bingbot/OAI-SearchBot should match the approved public policy. GPTBot training policy remains an independent owner decision.
5. At 390 and 1440 CSS pixels, inspect every route, navigation, media, custom 404 and both hero interest seeds. Verify zero page/hydration/console errors and deliberately disabled forms. Do not submit forms, invoke delivery or create appointments without a separate exact synthetic check grant.
6. Record deployment/domain/rule versions, timestamps, QA output and owner acceptance. Any P0 failure invokes rollback. Sitemap/indexing actions remain unauthorized until release QA is accepted and separately granted; never use Google Indexing API for ordinary service pages.

## Rollback — objective triggers and recovery owner

Immediately declare NO-GO/rollback for any TLS/host loop; missing/corrupt critical asset or route; any of the 12 patient routes non-200 on two consecutive checks 60 seconds apart; any HOLD row lost/converted to generic 404; wrong canonical/noindex on any patient route; admin exposure; or unapproved form activation. After launch, 5xx >=1% for five minutes with at least 100 requests (or any critical-route repeated failure at low volume) is a rollback trigger. Confirmed delivery failure is a trigger only if intake was separately approved and enabled. Do not use unconfirmed traffic loss as an immediate technical rollback signal.

1. Stop rollout; record incident ID, observed URL/status/SHA and start time. Freeze content writes to prevent mixed database state. Disable only separately authorized new intake if necessary; preserve received records in owner systems.
2. Hosting owner atomically restores prior version/origin and exact redirect/robots/cache configuration. DNS owner restores the recorded zone records if changed; account for original TTL propagation. Restore DB/uploads only if actually changed and under approved recovery procedure; avoid overwriting new records blindly.
3. Validate original critical homepage, implantation, prosthetics, microscope paths and all legacy HOLD fingerprints/statuses. Verify TLS, robots/sitemaps, www/path/query and old analytics/verification. Confirm mail DNS remained intact. Purge authorized stale caches and confirm a single old version.
4. Record time to recovery, evidence and incident cause. Target <=15 minutes; escalation owner must be named before launch. Retain failed artifact and logs securely. Schedule rework and a fresh authorization before retry. A rollback is not release closure.

## Post-launch observation — prepared, unscheduled

At 0 hours run synchronous routing/indexability/disabled-form QA above. At 24 hours repeat all priority routes, 64-row contract, crawl/robots/canonicals/sitemap and logs; separate DNS propagation and provider data latency. Sitemap submission or priority indexing needs separate authorization after QA.

At 7 days inspect errors, crawler access, indexing signals and attribution quality. At 28/90 settled days compare defined cohorts and equal durations for query/page/country/device/search appearance, organic landing sessions, identifiable AI referrals, delivered forms, connected calls, qualified leads, appointments and net revenue. Capture rank/AI samples with provider, exact query, location, device, date, personalization and limitations. A sample is not a stable rank. Annotate rollout, consent/tracking changes, seasonality and campaigns. Phone clicks remain intent; server receipts remain delivery; qualified leads/bookings require owned CRM confirmation. `outcome_report.claims=[]` until evidence passes the operator gate.
